# Importing from WordPress

WordPress is not a repository, so the connector cannot clone it. The route is an export, a
conversion, and then the same route verification everything else gets.

## 1. Export

**Tools → Export → All content.** You get a WXR file — WordPress's own XML dialect.

Take a database backup too. Not because this touches your database, but because you are
about to decide whether a decade of content survived a conversion, and you want the original
to check against.

## 2. Record every URL first

**Do this before anything else.** It is the whole safety net.

```bash
curl -s https://your-site.example.com/wp-sitemap.xml > before-sitemap.xml
```

Follow the sub-sitemaps if it is an index. If there is no sitemap, a crawl works; so does the
`wp_posts` table, joined to permalink structure.

Keep that file. It is what the route diff compares against, and a migration that loses URLs
without anyone noticing is the failure mode this whole page exists to prevent.

## 3. Convert

WXR carries HTML in `content:encoded`, not Markdown, so conversion is required. Any of the
usual tools work — the CMS cares about the _result_, not how you got there.

Map WordPress's fields onto the required eight:

| WordPress                         | Dheys                              |
| --------------------------------- | ---------------------------------- |
| `title`                           | `title`                            |
| `post_name`                       | `slug` — keep it, this is your URL |
| first category                    | `category`                         |
| `post_date_gmt`                   | `publishedDate`                    |
| `excerpt`, or the first paragraph | `excerpt`                          |
| site language                     | `locale`                           |
| author display name               | `author`                           |
| —                                 | `sourceType: imported`             |

**Keep `post_name` as the slug.** Every inbound link and every search result depends on it.
Tidying slugs during a migration is how a site loses its search presence in one afternoon.

Also carry over: tags, featured image (and its alt text — WordPress stores it as
`_wp_attachment_image_alt`), and the WordPress id, so you can trace anything back.

## 4. Check the conversion

```bash
pnpm typecheck
```

Content that does not validate fails the build with the file and the field named. Common
ones:

- **Missing `category`** — uncategorised posts. Give them a real category.
- **Missing `excerpt`** — WordPress often has none. Take the first paragraph.
- **Bad slugs** — uppercase or percent-encoded. Transliterate rather than re-inventing, and
  add a redirect if a slug genuinely has to change.
- **Shortcodes** — `[gallery]`, `[caption]` and friends survive conversion as literal text.
  Search for `[` at the start of a line.

## 5. Verify the routes

```bash
pnpm build
pnpm connect --from . --dry-run
```

Compare the built output against `before-sitemap.xml`. Every URL that existed must still
resolve, or be covered by a redirect whose destination exists.

## Things that do not come across

Stated plainly, because finding out later is expensive:

- **Comments.** No comment system ships. Export them separately if you want them.
- **Plugin-generated content.** Anything a plugin rendered at request time is not in the WXR.
- **Custom fields**, unless you map them explicitly.
- **Redirect plugin rules.** Export them and translate them into your host's redirect
  configuration.
- **Anything generated by a theme's PHP** rather than stored as content.

## Afterwards

Point DNS at the new host only once the route check passes. Keep the WordPress install
running, read-only, for a few weeks — it costs almost nothing and it is the difference
between a quick fix and an archaeology project.
